# Commit

변경사항을 분석해 컨벤션에 맞게 커밋한다.

## 절차

### 1. 변경사항 분석

아래를 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # 아직 stage하지 않은 변경
git diff --staged   # 이미 stage된 변경
git log --oneline -10   # 최근 커밋 스타일 참고
```

- 새로 추가된 untracked 파일도 내용을 읽어 확인한다.
- git 저장소가 아니거나 변경사항이 없으면 그 사실을 알리고 종료한다.
- `.env`, 키·토큰이 담긴 파일, `node_modules`, 빌드 산출물(`dist`)이 포함되어 있으면 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눈다.
- 파일 단위뿐 아니라 필요하면 hunk 단위(`git add -p` 대신 파일을 나눠 stage)로 구분한다.
- 서로 의존하는 변경(예: 컴포넌트와 그 테스트)은 같은 커밋에 둔다.
- 분류 결과를 "커밋 1: …, 커밋 2: …" 형태로 정리한다.

### 3. 한국어 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문(선택): 무엇을 왜 바꿨는지>
```

| type | 용도 |
| --- | --- |
| feat | 새 기능, 사용자에게 보이는 변경 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 기타 |

규칙:
- 요약은 한 줄, 50자 안팎, 마침표 없이 명사형 또는 `~한다/~추가` 중 하나로 일관되게 쓴다.
- 최근 `git log` 스타일이 있으면 그것을 따른다.
- 본문은 "무엇"보다 "왜"를 적는다. 자명한 변경이면 생략한다.
- 대화 중 시스템이 지정한 커밋 attribution 줄이 있으면 메시지 끝에 붙인다.

### 4. 바로 커밋

1. 승인을 기다리지 않고, 분류한 커밋 단위별로 대상 파일만 지정해 stage하고 커밋한다. `git add -A`나 `git add .`는 쓰지 않는다.
   - 여러 줄 메시지는 HEREDOC 또는 `-m`을 여러 번 사용해 전달한다.
2. 끝나면 `git log --oneline -n <커밋 수>`로 결과(커밋별 파일 목록과 메시지)를 사용자에게 보고한다.

## 하지 않는 것

- push, amend, `--no-verify`, force 옵션은 사용자가 명시적으로 요청하기 전에는 쓰지 않는다.
- pre-commit hook이 실패하면 우회하지 말고 원인을 고친 뒤 새 커밋을 만든다.
- 기본 브랜치(main/master)에 있다면 새 브랜치를 만들어 그 위에 커밋한다.
